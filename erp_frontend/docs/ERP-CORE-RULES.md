# ملف القواعد الأساسية — نظام ERP

**الإصدار:** 1.1
**المكدس التقني:** ASP.NET Core Web API + SQL Server + EF Core | React + Vite + TypeScript
**العملة الأساسية الافتراضية:** الدينار العراقي (IQD)
**الحالة:** ما قبل كتابة الكود — هذه القواعد تسبق أي جدول أو سطر برمجي
**الملف المرافق:** `backend-design-rules.md` — يحكم بنية الطبقات والتسمية ومعالجة الأخطاء. هذا الملف يحكم البيانات المالية. عند التعارض في أي أمر مالي، **الأسبقية لهذا الملف**.

---

## 0. كيف يُستخدم هذا الملف

هذا الملف **قانون** وليس توثيقاً. التوثيق يصف ما بُني؛ القانون يحدد ما يُسمح ببنائه.

**لأي وكيل ذكاء أو مطور يعمل على هذا النظام:**

1. اقرأ هذا الملف بالكامل قبل اقتراح أي جدول أو استعلام أو منطق مالي.
2. كل بند هنا قابل للفحص بجواب نعم أو لا. إن كان اقتراحك يخالف بنداً، فالاقتراح مرفوض — لا تبحث عن تسوية.
3. القواعد المعلّمة بـ **[صارم]** لا تُخالَف تحت أي ظرف ولا لأي طلب من المستخدم. إن طلب المستخدم مخالفتها، نبّهه إلى رقم القاعدة واشرح الأثر قبل التنفيذ.
4. القواعد المعلّمة بـ **[مؤجل]** ليست ممنوعة، بل خارج نطاق الإصدار الحالي. لا تبنِها ولا ترفضها مبدئياً.
5. عند إنشاء أي جدول جديد، مرّره على **قائمة الفحص** في القسم 13 قبل اعتماده.
6. أي تعديل على هذا الملف يرفع رقم الإصدار ويُسجَّل في القسم 15.

**المبدأ الحاكم لكل ما يلي:**

> كل مبلغ في النظام يجب أن يملك هوية كاملة: القيمة، والعملة، وسعر الصرف، وتاريخ السعر، ومعنى المبلغ.
> أي مبلغ ينقصه واحد من هذه الخمسة هو خطأ مستقبلي مؤجل.

## 1. المفاهيم الثلاثة للعملة — الفصل الإلزامي

النظام يفصل بين ثلاثة مفاهيم لا تختلط أبداً:

| المفهوم | التعريف | أين يُخزَّن |
|---|---|---|
| **عملة المعاملة** (Transaction Currency) | العملة التي حدثت بها العملية فعلاً | تُخزَّن في المستند والقيد |
| **عملة الدفاتر** (Base / Functional Currency) | عملة القوائم المالية والحسابات الختامية | خاصية الشركة، تُخزَّن مقابلها في كل سطر |
| **عملة العرض** (Presentation Currency) | ما يراه المستخدم على الشاشة أو التقرير | **لا تُخزَّن إطلاقاً** — تُحسب عند العرض |

**R-CUR-01 [صارم]** — تغيير عملة العرض لا يغيّر أي رقم مخزَّن في قاعدة البيانات. هي عملية قراءة بحتة.

**R-CUR-02 [صارم]** — لا يوجد في النظام مسار واحد يسمح لعملة العرض بالكتابة في جدول.

**R-CUR-03 [صارم]** — عملة الدفاتر خاصية للشركة (`Company.BaseCurrencyId`)، وهي **مصدر الحقيقة الوحيد**. يُمنع وجود أي إعداد آخر أو حقل آخر في النظام يمثل عملة الأساس.

## 2. عملة الأساس — التثبيت والقفل

**R-BASE-01 [صارم]** — عملة الأساس تُختار مرة واحدة عند تأسيس الشركة، وتُقفل نهائياً عند أول عملية مالية.

**R-BASE-02 [صارم]** — القفل يُمثَّل بحقل `Company.IsBaseCurrencyLocked BIT NOT NULL DEFAULT 0`.
- يُرفع تلقائياً إلى `1` عند أول عملية مالية من **أي** نوع.
- **لا يُخفض أبداً**، ولا توجد شاشة أو صلاحية أو دور يسمح بخفضه.

**R-BASE-03 [صارم]** — "أول عملية مالية" لا تعني أول قيد فقط. القفل يُرفع عند أول واحدة من:
- قيد محاسبي مرحَّل
- رصيد افتتاحي لأي حساب
- رصيد افتتاحي لعميل أو مورد
- تكلفة افتتاحية لصنف
- أي سطر في قائمة أسعار

**R-BASE-04 [صارم]** — القفل يُنفَّذ في **قاعدة البيانات** عبر TRIGGER، وليس في طبقة الكود فقط. السبب: أي تعديل مباشر على القاعدة يجب أن يُمنع أيضاً.

**R-BASE-05 [مؤجل]** — تغيير عملة الدفاتر لمنشأة قائمة (Functional Currency Change) **غير مدعوم ولن يُبنى**. هو معيار محاسبي كامل يتطلب: تاريخ انتقال، أرصدة ختامية وافتتاحية مترجمة، معالجة الأصول والالتزامات وحقوق الملكية، وفروقات الترجمة، ومعالجة المستندات المفتوحة.
البديل المعتمد: تُفتح شركة جديدة في النظام بأرصدة افتتاحية مترجمة يدوياً.
*هذا القرار يُلغي فئة كاملة من المخاطر بسطر واحد بدل بنائها.*

## 3. أسعار الصرف

**R-FX-01 [صارم]** — جدول أسعار الصرف يخزّن العملتين **صراحة**، ولا يعتمد على "مقابل العملة الأساسية" ضمنياً:

```
FxRate:
  FromCurrencyId   -- العملة الأولى
  ToCurrencyId     -- العملة الثانية
  Rate             DECIMAL(28,12)
  RateDate         DATE
  RateSource       -- رسمي / سوق / متفق عليه مع المورد
```

السبب: السعر المخزَّن يجب أن يجيب دائماً على سؤال محدد لا لبس فيه.

**R-FX-02 [صارم]** — تعريف الاتجاه الموحّد: `Rate` = كم وحدة من `ToCurrency` تساوي **وحدة واحدة** من `FromCurrency`.
مثال: `From=USD, To=IQD, Rate=1320` تعني أن دولاراً واحداً = 1320 ديناراً.

**R-FX-03 [صارم]** — يُمنع اشتقاق الاتجاه العكسي بالمقلوب الحسابي (`1 / Rate`) في أي حساب مالي مخزَّن. كل اتجاه يحتاجه النظام يُخزَّن كصف مستقل.
السبب: المقلوب ينتج أخطاء تقريب تراكمية، وتتضخم عبر عمليات التحويل المتتالية.

**R-FX-04 [صارم]** — دقة السعر `DECIMAL(28,12)`. السبب: السعر الأقل من واحد يفقد معناه سريعاً بدقة أقل.

**R-FX-05 [صارم]** — سعر الصرف يُخزَّن **داخل المستند والقيد نفسه**، ولا يُقرأ من جدول الأسعار وقت التقرير. الفاتورة المرحَّلة بسعر 1320 تبقى 1320 إلى الأبد.

**R-FX-06 [صارم]** — يُسمح للمستخدم بتجاوز السعر الرسمي بسعر متفق عليه فعلياً، ويُخزَّن `RateSource` للتمييز.
السبب: في السوق العراقي الفرق بين السعر الرسمي وسعر السوق حقيقي ويومي، وإجبار المستخدم على السعر الرسمي ينتج دفاتر لا تطابق الواقع.

## 4. تمثيل المبالغ

**R-AMT-01 [صارم]** — لا يوجد في النظام **جدول واحد** يحتوي عمود مبلغ دون عمود عملة يقابله. هذه قاعدة تُفحص عند إنشاء كل جدول.

**R-AMT-02 [صارم]** — كل سطر مالي يحمل الحقول الخمسة:

| الحقل | النوع | المعنى |
|---|---|---|
| `CurrencyId` | INT | عملة المعاملة |
| `ExchangeRate` | DECIMAL(28,12) | السعر المستخدم في هذه العملية تحديداً |
| `ExchangeRateDate` | DATE | تاريخ السعر |
| `AmountFC` | DECIMAL(19,4) | المبلغ بعملة المعاملة |
| `AmountBase` | DECIMAL(19,4) | المقابل بعملة الدفاتر |

**R-AMT-03 [صارم]** — كل مستند تجاري (فاتورة، أمر شراء، سند، عرض سعر، دفعة) يحمل `CurrencyId` في رأسه، وكل سطر يرث عملة الرأس.

**R-AMT-04 [صارم]** — أنواع البيانات:
- المبالغ والتكاليف: `DECIMAL(19,4)`
- أسعار الصرف: `DECIMAL(28,12)`
- الكميات: `DECIMAL(19,6)`
- **يُمنع منعاً باتاً** استخدام `FLOAT` أو `REAL` أو `DOUBLE` في أي حقل مالي أو كمي.

**R-AMT-05 [صارم]** — معنى كل مبلغ يجب أن يكون صريحاً في اسم العمود. يُمنع اسم عام مثل `Amount` وحده. الأسماء المعتمدة:
`AmountFC` / `AmountBase` / `UnitPriceFC` / `UnitCostBase` / `RemainingFC` / `RemainingBaseHistorical` / `CurrentValueBase`

**R-AMT-06 [صارم]** — عدد الخانات العشرية للعرض خاصية للعملة (`Currency.DecimalPlaces`)، لا ثابت في الكود.
IQD = 0، USD = 2، EUR = 2.

**R-AMT-07 [صارم]** — التقريب يحدث **مرة واحدة عند العرض فقط**. يُمنع التقريب في الخطوات الحسابية الوسيطة. سياسة التقريب مركزية في دالة واحدة، ولا تُكرَّر.

## 5. القيد المحاسبي

**R-GL-01 [صارم]** — التوازن يُفرض على `AmountBase` حصراً. قيد يخلط عملتين لا يتوازن إلا بعد التوحيد.

**R-GL-02 [صارم]** — التوازن يُفرض في قاعدة البيانات (CHECK / TRIGGER)، لا في طبقة الكود فقط. أي قيد غير متوازن يُرفض على مستوى القاعدة.

**R-GL-03 [صارم]** — القيد المرحَّل **لا يُعدَّل ولا يُحذف**. التصحيح يتم بقيد عكسي فقط.

**R-GL-04 [صارم]** — يُمنع الترحيل في فترة مالية مقفلة.

**R-GL-05 [صارم]** — كل الترحيل المحاسبي يمر عبر **طبقة واحدة مركزية**. لا تكتب أي وحدة قيداً بنفسها، مهما كان بسيطاً.

**R-GL-06 [صارم]** — **توازن القيد ليس دليلاً على صحة العملية.** خطأ في سعر الصرف قد ينتج قيداً متوازناً ومعبراً عن قيمة اقتصادية خاطئة.
الضمانات المقابلة: R-FX-05 (تثبيت السعر)، R-PAY-04 (فرق الصرف المحقق)، R-TRC-01 (الهوية الموحدة).

**R-GL-07 [صارم]** — شجرة الحسابات تحتوي منذ اليوم الأول على حسابات فروقات العملة، بفرعيها:
- فروقات صرف **محققة** (Realized) — ربح وخسارة
- فروقات صرف **غير محققة** (Unrealized) — ربح وخسارة

## 6. الدفعات والتسويات

**R-PAY-01 [صارم]** — الدفعة **حدث نقدي مستقل**، وليست خاصية للفاتورة. توجد ولها معنى كامل حتى لو لم ترتبط بأي فاتورة (دفعة مقدمة، مبلغ تحت التسوية).

**R-PAY-02 [صارم]** — النموذج ثلاثي الجداول، لا ثنائي:

```
Invoice              -- الالتزام الأصلي، بعملته وسعره التاريخي
Payment              -- الحدث النقدي: عملة، مبلغ، سعر صرف، تاريخه، صندوق/بنك
PaymentAllocation    -- تخصيص جزء من دفعة لفاتورة معينة
```

جدول التخصيص هو الحل الوحيد للحالات التالية، وكلها **حالات عادية لا استثنائية**:
- دفعة واحدة لعدة فواتير
- دفعة جزئية
- فاتورة بالدولار ودفعة بالدينار (والعكس)
- دفعة مقدمة قبل إنشاء الفاتورة
- مبلغ غير مخصص ينتظر التوزيع

**R-PAY-03 [صارم]** — كل دفعة تحمل: العملة، المبلغ، سعر الصرف، تاريخ السعر، الصندوق أو الحساب البنكي، وارتباطاً صريحاً بالقيد الناتج عنها.

**R-PAY-04 [صارم]** — فرق الصرف المحقق يُحسَب ويُخزَّن على مستوى **صف التخصيص** (`PaymentAllocation`)، لا على مستوى الدفعة.
السبب: الفرق بين سعر الفاتورة وسعر السداد يتحدد لحظة التخصيص لا لحظة الدفع.

**R-PAY-05 [صارم]** — الفرق بين سعر الفاتورة وسعر السداد **ليس تعديلاً على الفاتورة**. هو ربح أو خسارة صرف يُرحَّل لحساب فروقات العملة المحققة. قيمة الفاتورة الأصلية لا تُمس.

**R-PAY-06 [صارم]** — كل دفعة تنتج **حركة نقدية فعلية** في الصندوق أو البنك. يُمنع وجود دفعة لها أثر في الذمم وقيد محاسبي دون حركة نقدية مقابلة.

**R-PAY-07 [صارم]** — حذف الدفعة ممنوع. الإلغاء يتم بعكس القيد وعكس الحركة النقدية وإلغاء التخصيصات، في معاملة ذرية واحدة.

## 7. الذمم والأرصدة

**R-AR-01 [صارم]** — يُمنع جمع مبالغ من عملات مختلفة في خانة واحدة دون ترجمة. `1000 USD + 500,000 IQD` ليس رصيداً ذا معنى.

**R-AR-02 [صارم]** — رصيد العميل أو المورد يُحفَظ ويُعرَض بالعملتين معاً: بعملة المعاملة (ما تطالبه به فعلاً) وبعملة الدفاتر (للتقارير).

**R-AR-03 [صارم]** — المتبقي من الفاتورة **ثلاثة أرقام مختلفة** لا رقم واحد:

| الرقم | التخزين | الاستخدام |
|---|---|---|
| المتبقي بعملة الفاتورة | يُخزَّن | المطالبة الفعلية |
| قيمته بالسعر التاريخي | يُخزَّن | الرقم المثبت في الدفاتر |
| قيمته بسعر اليوم | **يُحسَب عند الطلب** | التقييم في نهاية الفترة (فرق غير محقق) |

**R-AR-04 [صارم]** — لا تخلط بين الفرق المحقق (عند السداد) والفرق غير المحقق (عند التقييم). حسابان منفصلان ومنطقان منفصلان.

**R-AR-05 [صارم]** — تجميع الأرصدة يعتمد على القيم المترجمة، لا على أرقام المستندات الأصلية مباشرة.

## 8. المخزون والتكلفة

هذه أخطر منطقة في النظام، لأن الخطأ فيها **تراكمي ولا يبقى في مستند واحد**.

**R-INV-01 [صارم]** — تكلفة المخزون تُحسَب وتُخزَّن **بعملة الدفاتر حصراً**. لا يوجد حقل تكلفة بعملة أجنبية في أي جدول مخزون.

**R-INV-02 [صارم]** — مصدر التكلفة هو `AmountBase` المحسوب من النظام، **وليس رقماً يدخله المستخدم بعد تحويل يدوي**.

**R-INV-03 [صارم]** — حدّ التحويل صريح ومعرَّف:
```
سعر الشراء بعملة المستند
        ↓  (تحويل داخل النظام بسعر مسجَّل ومؤرَّخ)
القيمة بعملة الدفاتر
        ↓
دخول التكلفة إلى المخزون
```
يُمنع أن يكون هذا الحد ضمنياً أو موزعاً على عدة طبقات.

**R-INV-04 [صارم]** — مصاريف الاستيراد (Landed Cost) قد تأتي بعملة ثالثة مختلفة عن عملة البضاعة. كل مصروف يُحوَّل بسعره وتاريخه الخاص **قبل** توزيعه على تكلفة الأصناف.
مثال واقعي: بضاعة باليورو، شحن بالدولار، جمارك بالدينار.

**R-INV-05 [صارم]** — دقة التحويل ودقة تخزين التكلفة متطابقتان. يُمنع التحويل بدقة ثم التخزين بدقة أقل، لأن القطع المبكر يتضخم عند الضرب في كميات كبيرة.

**R-INV-06 [صارم]** — أي تعديل على منطق التكلفة بعد بدء التشغيل يتطلب خطة إعادة حساب صريحة. متوسط التكلفة تراكمي ولا يُصلَح بأثر رجعي بسهولة.

## 9. دورة حياة المستندات — الإلغاء والتصحيح

**R-LIFE-01 [صارم]** — البيانات الأساسية (عملاء، أصناف، حسابات): تُعطَّل أو تُحذف منطقياً (Soft Delete). لا حذف فعلي إن كانت مرتبطة بحركة.

**R-LIFE-02 [صارم]** — المستند المالي المرحَّل: **يُلغى أو يُعكَس**، ولا يُحذف.

**R-LIFE-03 [صارم]** — القيد المرحَّل: لا يُعدَّل مباشرة إطلاقاً. (تكرار مقصود لـ R-GL-03 لأهميته.)

**R-LIFE-04 [صارم]** — كل مستند مالي له دورة حياة معرَّفة صراحة تحدد:
- متى يمكن تعديله
- متى يتوقف تعديل السعر وسعر الصرف
- متى يصبح ملتزماً محاسبياً (Committed)
- متى يصبح العكس إلزامياً بدل التعديل

**R-LIFE-05 [صارم]** — إزالة المستند من الشاشة لا تعني اختفاء أثره المحاسبي. يُمنع أي مسار يترك الذمم مختلفة عن دفتر الأستاذ العام.

## 10. الهوية الموحدة للحركة والتتبع

**R-TRC-01 [صارم]** — كل عملية اقتصادية تُولِّد `TransactionId` واحداً (GUID)، يُنسَخ في **كل** أثر تنتجه:
- حركة المخزون
- القيد المحاسبي
- الحركة النقدية
- سطر الذمة
- سطر التخصيص

**R-TRC-02 [صارم]** — سلسلة التتبع يجب أن تكون قابلة للمراجعة كاملة باستعلام واحد:
```
المستند التجاري → الحركة المالية → الحركة النقدية → القيد المحاسبي → أثر التقرير
```

**R-TRC-03 [صارم]** — يجب أن يوجد فحص آلي دوري (Reconciliation Job) يتحقق من اتساق كل آثار الـ `TransactionId` الواحد. الوحدات لا تسجل من منظورها المنفصل — كلها تمثل **نفس الحدث الاقتصادي**.

**R-TRC-04 [صارم]** — سجل التدقيق (Audit Trail) يُبنى في المرحلة صفر. من عدّل، ماذا، ومتى، والقيمة قبل وبعد. إضافته لاحقاً شبه مستحيلة.

## 11. التقارير

**R-RPT-01 [صارم]** — التقارير المحاسبية تعتمد على **القيم المثبتة في الدفتر**، لا على قيم المستندات. القيمة في المستند ليست بالضرورة القيمة المحاسبية.

**R-RPT-02 [صارم]** — كل تقرير يعلن صراحة في رأسه: هل يعرض بعملة المعاملة أم بعملة الدفاتر. هذا المعنى **ثابت ولا يتغير من تقرير لآخر**.

**R-RPT-03 [صارم]** — يُمنع في أي تقرير جمع مبالغ من عملات مختلفة دون ترجمة صريحة معلنة.

**R-RPT-04 [صارم]** — يُمنع كتابة رمز عملة ثابتاً (Hardcoded) في أي شاشة أو تقرير أو مستند مطبوع.

**R-RPT-05 [صارم]** — يوجد **مكوّن عرض واحد** يستقبل (المبلغ + معرّف العملة) معاً. لا يُعرض أي مبلغ في النظام إلا عبره.

**R-RPT-06 [صارم]** — إن ظهر مبلغ لا تُعرف عملته، يُعرض **خطأ** لا رقم مجرد. الرقم بلا عملة صحيح عددياً وخاطئ في معناه، وهذا أسوأ من عدم عرضه.

## 12. حدود API والواجهة

المشروع مفصول: خلفية `ASP.NET Core Web API` وواجهة `React + Vite + TypeScript`. الفصل يخلق حدوداً جديدة يمكن أن تتسرب منها القواعد المالية.

**R-API-01 [صارم]** — كل منطق مالي أو محاسبي في الخلفية حصراً. الواجهة **لا تحسب، لا تحوّل عملة، لا تجمع أرصدة، لا تقرّب مبالغ، لا تشتق مجاميع**. تعرض ما يصلها فقط.
امتداد مباشر لـ R-GL-05.

**R-API-02 [صارم]** — كل مبلغ يُنقل عبر API ككائن كامل لا رقم مجرد:

```json
{
  "amountFC": "1000.0000",
  "currencyId": 2,
  "currencyCode": "USD",
  "exchangeRate": "1320.000000000000",
  "exchangeRateDate": "2026-09-03",
  "amountBase": "1320000.0000"
}
```

يُمنع إرسال رقم عارٍ بلا عملة. هذا تطبيق R-AMT-01 على حدود الشبكة.

**R-API-03 [صارم]** — المبالغ وأسعار الصرف تُنقل في JSON **كنصوص (string)** لا كأعداد.
السبب: `Number` في JavaScript يفقد الدقة فوق 2^53، ومليار دينار رقم يومي في هذا النظام. يُنفَّذ عبر `JsonConverter` عالمي مسجَّل مرة واحدة، لا في كل DTO. في الواجهة تُستخدم `decimal.js` أو `big.js` للعرض، لا للحساب (R-API-01).

**R-API-04 [صارم]** — أنواع TypeScript **مولَّدة آلياً من OpenAPI**. يُمنع كتابة أي نموذج يدوياً يعكس كياناً في الخلفية.
السبب: مطوّر واحد يصون نموذجين متطابقين يدوياً سيُنتج تناقضاً حتمياً. التوليد شرط بقاء لا تحسين.

**R-API-05 [صارم]** — التحقق يتكرر في الطبقتين: تحقق الواجهة **للتجربة فقط**، وتحقق الخلفية **هو المعتبر**. يُمنع الاعتماد على تحقق الواجهة لأي قاعدة مالية.

**R-API-06 [صارم]** — كل عملية مالية تُنفَّذ عبر **نقطة نهاية واحدة ذرّية** تُنشئ المستند وقيده وحركاته النقدية والمخزنية في معاملة واحدة.
يُمنع تنفيذ عملية مالية عبر عدة نداءات متتابعة من الواجهة (أنشئ فاتورة ← أنشئ قيداً ← حدّث المخزون)، لأن انقطاعاً في المنتصف يترك النظام في حالة غير متسقة لا يكتشفها أحد.

**R-UI-01 [صارم]** — مكوّنات الواجهة لا تحتوي منطقاً مالياً. الصفحة تستدعي وتعرض فقط. الغرض: إعادة بناء الواجهة لاحقاً تكلّف أياماً لا شهوراً.

**R-UI-02 [صارم]** — يوجد مكوّنان وحيدان للمبالغ: `<MoneyDisplay>` و `<MoneyInput>`، وكلاهما يستقبل (المبلغ + العملة) معاً. **لا يُعرض ولا يُدخَل أي مبلغ في النظام خارجهما.**
هذا هو التطبيق العملي لـ R-RPT-04 و R-RPT-05 و R-RPT-06.

**R-UI-03 [مؤجل]** — صقل الواجهة يبدأ بعد استقرار النموذج المالي (بعد المرحلة الخامسة). قبل ذلك تُبنى **واجهة تشغيلية** فقط: شبكة، نموذج إدخال، حفظ، عرض خطأ واضح. الغرض منها التحقق من المنطق بإدخال بيانات حقيقية، لا أن تكون منتجاً.

## 13. قائمة الفحص — تُطبَّق على كل جدول جديد

قبل اعتماد أي جدول، أجب بنعم على كل بند:

- [ ] هل كل عمود مبلغ يقابله عمود عملة؟ (R-AMT-01)
- [ ] هل اسم كل عمود مبلغ يوضح معناه صراحة (FC / Base / تاريخي / حالي)؟ (R-AMT-05)
- [ ] هل الأنواع `DECIMAL` بالدقة الصحيحة، وخالية تماماً من `FLOAT`؟ (R-AMT-04)
- [ ] هل يحمل السطر سعر الصرف وتاريخه، أم يعتمد على قراءة لاحقة؟ (R-FX-05)
- [ ] هل يحمل الجدول `TransactionId` للربط بباقي آثار العملية؟ (R-TRC-01)
- [ ] هل يحمل حقول التدقيق (من، متى)؟ (R-TRC-04)
- [ ] هل الحذف منطقي وليس فعلياً؟ (R-LIFE-01)
- [ ] هل القيود المحاسبية والتوازن مفروضة في القاعدة لا في الكود فقط؟ (R-GL-02)
- [ ] هل يوجد مصدر حقيقة واحد لكل قيمة جوهرية، دون تكرار في مكانين؟ (R-CUR-03)
- [ ] إن كان الجدول يتعلق بالتكلفة: هل التكلفة بعملة الدفاتر حصراً؟ (R-INV-01)
- [ ] هل كل حقل `decimal` له `HasPrecision` صريح، ولم يُترك لافتراضي EF Core `(18,2)`؟ (R-AMT-04)
- [ ] إن كان الجدول مالياً مرحَّلاً: هل هو **خالٍ** من `IsDeleted` ومن Query Filter؟ (R-LIFE-02)
- [ ] هل التواريخ المحاسبية `DateOnly` منفصلة عن التواريخ التقنية UTC؟ (R-GL-04)
- [ ] هل الـ DTO المقابل ينقل المبالغ ككائن عملة كامل ونصوص لا أعداد؟ (R-API-02, R-API-03)

## 14. نطاق الإصدار الأول — ما يُبنى وما يُؤجَّل

### يُبنى الآن (بنية + منطق)
- الحقول الخمسة في كل سطر مالي
- جدول العملات وجدول أسعار الصرف باتجاهات صريحة
- `Company.BaseCurrencyId` + قفل التثبيت
- محرك القيود المركزي مع فرض التوازن في القاعدة
- نموذج الدفعة والتخصيص الثلاثي
- فروقات الصرف المحققة
- تكلفة المخزون بعملة الدفاتر + Landed Cost
- `TransactionId` وسجل التدقيق
- مكوّنا `<MoneyDisplay>` و `<MoneyInput>`
- توليد أنواع TypeScript من OpenAPI (يُعدّ منذ اليوم الأول)
- المكوّنات المشتركة في React: شبكة، نموذج، منتقي حساب، منتقي صنف

### بنية الآن، منطق لاحقاً
- **العرض التقريري بعملة أخرى** — رخيص، لكن ليس أولوية
- **مستند صرف العملة** — يُبنى مع الصناديق والخزينة (المرحلة الرابعة)، لا يُؤجَّل أكثر
- **فروقات الصرف غير المحققة** — تُبنى مع إقفال الفترة
- **عملة أساس مختلفة لكل شركة** — الحقل موجود، لكن التقارير الموحدة عبر شركات مختلفة العملات مؤجلة

### لا يُبنى
- **تغيير عملة الدفاتر لمنشأة قائمة** (R-BASE-05)
- **التقارير المالية الموحدة متعددة العملات** — تحتاج معايير ترجمة كاملة
- **وحدة المقاولات والمشاريع** — منطق مالي موازٍ (مستخلصات، نسبة إنجاز، محتجزات، أوامر تغيير)، تُؤجَّل للسنة الثانية
